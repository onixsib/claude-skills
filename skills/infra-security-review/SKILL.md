# Ревью безопасности инфраструктуры

Скилл ищет ошибки, из-за которых инфраструктура становится доступна шире, чем задумано: секреты утекают, права шире нужного, защита выключается одной опцией, изменение нельзя откатить. Проверяет и чужую работу, и свою: код, написанный в этой же сессии, проверяется с тем же пристрастием.

## Правила работы

Эти правила важнее полноты ревью.

1. **Только чтение.** Ревью ничего не меняет: ни в репозитории, ни в кластерах, ни во внешних системах. Разрешено: `git diff/log/show/blame`, `helm template`, `grep`, чтение файлов, `kubectl get/describe/logs`, GET-запросы к API. Запрещено: `apply`, `patch`, `delete`, `exec` с изменениями, `git checkout` поверх рабочего дерева, запись в Vault. Исправления — предложением в отчёте, применяет человек. Без запроса разрешения скилл может запускать только команды из `allowed-tools` (git на чтение, `helm template/lint`, `kubectl get/describe/logs/auth can-i`); всё остальное, включая `curl` к API, идёт через обычный запрос разрешения.
2. **Правила окружений проекта выше скилла.** Если в CLAUDE.md или памяти сказано, что prod и stage — только с разрешения, к ним не обращаться даже на чтение без явного «да». По умолчанию ревью идёт по коду и по dev/test.
3. **Секреты не показывать.** Найденный секрет не печатать целиком ни в чате, ни в отчёте: указывать файл, строку, тип и первые 4 символа. Вывод команд, которые могут содержать секреты, маскировать до показа (см. `references/secrets.md`, раздел «Маскирование»). Не доставать секреты из Vault или кластера, чтобы «проверить, что они настоящие».
4. **Утечка — сразу наверх.** Если секрет уже попал туда, откуда его могут прочитать другие (git, логи, статус CR, общий чат), это отдельная строка в начале ответа с рекомендацией ротации, а не пункт в середине отчёта.
5. **Доказательства, а не подозрения.** Каждая находка подкрепляется конкретным местом (файл:строка, объект, вывод команды) и сценарием: кто, что сделает, что получит. Без сценария — это вопрос, а не находка.

## Порядок работы

### 1. Определить объём

- **Дифф MR или ветки:** `git diff <base>...HEAD --stat`, затем по файлам. Смотреть и удалённые строки: снятая проверка опаснее добавленной.
- **Файлы или каталог:** перечислить, что входит; генерируемое (Helm) рендерить `helm template` с теми values, с которыми оно реально едет.
- **Живое состояние** (только по правилам окружений): какие кластеры и системы, только чтение.
- **Своя работа в этой сессии:** перечислить всё созданное и изменённое — файлы, скрипты, MR, команды, отданные пользователю на запуск.

### 2. Пройти чеклисты по типам содержимого

| Что в объёме | Чеклист |
| --- | --- |
| Любые файлы, логи, скрипты, вывод команд | `references/secrets.md` — всегда |
| Политики, роли, auth-методы, PKI Vault | `references/vault.md` |
| Манифесты Kubernetes, RBAC, вебхуки, Job'ы | `references/kubernetes.md` |
| Helm, ArgoCD, GitOps-структура values | `references/gitops-helm.md` |
| Crossplane: композиции, XRD, провайдеры | `references/crossplane.md` |
| Shell-скрипты, команды для запуска | `references/scripts.md` |

Чеклисты — минимум, а не потолок. Если что-то выглядит опасным и не попадает ни в один пункт, это тоже находка.

### 3. Проверить каждую находку

Перед тем как включить находку в отчёт:

- **Достижимость.** Значение действительно доезжает до рантайма? Проверить переопределения values, условия `if` в шаблонах, `managementPolicies`, какой объект реально рендерится.
- **Компенсирующие меры.** Широкая роль, но mount недоступен по сети; секрет в values, но это плейсхолдер AVP `<path:...>`; `*` в политике, но ограничено шаблоном `{{identity...}}`. Учитывать, но не считать проблему закрытой, если защита держится на одном допущении.
- **Масштаб.** Один namespace, кластер, весь контур или чужой контур (test → prod).
- **Ложные срабатывания** выкидывать молча; сомнительное — в раздел «Вопросы».

### 4. Отчёт

Формат — `references/report.md`. Порядок: утечки, требующие ротации → критичные → высокие → средние → низкие → вопросы → что не проверено. Для каждой находки: место, суть, сценарий, исправление, как проверить исправление.

Отчёт идёт в чат. Файл отчёта создавать, только если попросили, и никогда — внутри проверяемого репозитория.

## Шкала серьёзности

| Уровень | Критерий | Примеры |
| --- | --- | --- |
| Критично | Любой участник с минимальным доступом получает чужие секреты, админские права или ломает прод; или секрет уже утёк | роль Vault на любые SA с доступом ко всему KV; токен в логах Job; `cluster-admin` на `system:serviceaccounts` |
| Высокое | Одна ошибка конфигурации или один скомпрометированный компонент даёт эскалацию | approle, который может переписать свою политику; `deletionPolicy: Delete` на подхваченном внешнем ресурсе; `Replace=true` на CRD с данными |
| Среднее | Нужен дополнительный шаг или условие | плавающий тег образа провайдера; нет audit device; долгоживущий токен без ротации |
| Низкое | Гигиена, затрудняет расследование или будущие изменения | токен в переменной окружения дольше нужного; отсутствие `set -u` |

## Чего не делать

- Не «исправлять заодно» — ревью и правка разделены.
- Не запускать сканеры, которые сами ходят в сеть или в кластер (`kubectl apply -f https://...`, kube-bench как Job), без явного разрешения.
- Не считать документацию защитой: «в README написано не ставить true» — не мера.
- Не смягчать находку в своей работе. Если в этой сессии сам написал скрипт, печатающий токен, — это Критично, как и у любого другого.
