# Секреты

Проверяется всегда, при любом объёме ревью.

## Где ищем

- **Git:** открытые значения в values, vars, манифестах, скриптах, примерах, тестах. История тоже: удалённый из HEAD секрет живёт в `git log -p`.
  - Плейсхолдеры AVP (`<path:secret/data/...#key>`), ссылки на Secret, `secretKeyRef` — норма.
  - `kind: Secret` с `data`/`stringData` в репозитории без шифрования (sops, sealed-secrets) — находка. base64 — не шифрование.
- **Логи:** скрипт или Job печатает токен, пароль, `secret_id`, kubeconfig, приватный ключ. Типичное:
  - `echo "TOKEN: ${TOKEN}"` и «отладочные» выводы переменных;
  - `set -x` в скрипте, где есть секреты;
  - `cat` файла с ключом «для проверки»;
  - вывод CLI, который возвращает секрет (`vault write auth/.../login` без `-field`, `kubectl get secret -o yaml`).
  Логи Job'ов и подов уходят в общий сбор логов: считать утёкшим всё, что напечатано.
- **Аргументы процессов:** секрет в командной строке виден в `ps`, `/proc/*/cmdline`, в истории шелла, в аудите k8s (`args` пода). `curl -H "X-Vault-Token: $T"` светит токен в `ps`. Лучше заголовок через stdin или файл (`-H @-`, `-H @<(printf ...)`).
- **Переменные окружения:** видны в `kubectl describe pod` (если не из Secret), наследуются дочерними процессами, попадают в дампы. Для долгоживущих секретов — смонтированный файл.
- **Статус и аннотации объектов:**
  - `kubectl.kubernetes.io/last-applied-configuration` хранит всё, что применили, включая `stringData`;
  - статус CR контроллеров, которые зеркалят чужие объекты (`status.atProvider.manifest` у Crossplane `Object`), — проверить, не попадают ли туда `data` Secret'ов;
  - ConfigMap вместо Secret для чувствительных значений.
- **Артефакты и вывод:** CSV, отчёты, снимки состояния, скрипты в scratchpad, ответы в чате. Accessor'ы, `role_id`, `secret_id`, JWT, `hvs.`/`hvb.`/`s.`-токены туда не пишутся.

## Долгоживущие учётные данные

- SA-токены типа `kubernetes.io/service-account-token` не истекают. Особенно опасны у SA с `system:auth-delegator`, `cluster-admin`, правами на `secrets`.
- approle с `secret_id_ttl: 0` и `secret_id_num_uses: 0` — бессрочный логин.
- root-токен Vault в заметках, скриптах, переменных окружения. Root-токен нужен для аварий, а не для повседневного чтения; для чтения — короткий токен с узкой политикой.
- Kubeconfig с клиентским сертификатом admin, скопированный за пределы управляющего кластера.

## Утечка уже случилась

Если секрет оказался в git, логах, статусе объекта, чате, тикете:
1. Первой строкой отчёта: что утекло, где, кто мог прочитать.
2. Рекомендация: ротация (перевыпуск), затем отзыв старого. Удаление из лога или истории git не отменяет ротацию.
3. Устранить источник, иначе новый секрет утечёт тем же путём.

## Маскирование вывода

Перед показом вывода команд, который может содержать секреты:

```bash
sed -E 's/hv[sbr]\.[A-Za-z0-9._-]+/<vault-token>/g;
        s/eyJ[A-Za-z0-9._-]{20,}/<jwt>/g;
        s/("?(secret_id|role_id|token|password|passwd|private_key|client_secret)"?\s*[:=]\s*)"?[^",} ]+"?/\1<скрыто>/Ig' \
| awk '/-----BEGIN [A-Z ]*PRIVATE KEY-----/{print "<private-key>"; skip=1} skip&&/-----END/{skip=0; next} !skip'
```

Маскирование — страховка, а не разрешение читать секреты.
